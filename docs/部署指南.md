# 部署指南

Web Video Player 的前端和后端可以部署在同一主机或不同主机。前端是静态文件，后端是 Node.js 无状态信息代理；媒体地址始终由浏览器直连，不经过后端。

## 1. 部署模型

```text
浏览器
├─ HTTPS -> 前端静态站点
├─ HTTPS -> Node 后端 /health
├─ HTTPS -> Node 后端 /api/proxy/v2/request
└─ HTTPS -> Provider 返回的 MP4/HLS 媒体地址

Node 后端
└─ HTTPS -> Provider 指定的信息页面/API
```

公网前端必须连接 HTTPS 后端，否则浏览器会阻止混合内容。后端 `allowedOrigins` 必须精确包含前端 Origin。

## 2. 构建前端

先根据部署路径修改 `config/frontend.config.js`：

- `runtime.backendOrigin`：后端公开 Origin，不含 API 路径。
- `build.basePath`：站点部署在域名根时为 `/`，仓库子路径部署时为对应基础路径。

执行：

```bash
npm --prefix client ci
npm run build:frontend
```

发布 `client/dist/` 中的全部文件。产物中的 `config/frontend.config.js` 会被浏览器在主程序前读取；只修改其中 `runtime.backendOrigin` 后刷新即可生效。修改 `build.basePath` 必须重新构建，因为资源路径已经写入 HTML 和产物。

静态服务器必须把未知前端路由回退到 `index.html`。GitHub Pages 使用项目生成的 `404.html` 完成 history 路由回退。

## 3. GitHub Pages

仓库包含 `.github/workflows/deploy-pages.yml`，当前公开仓库在 `main` 推送或手动触发时：

1. 使用 Node.js 20 安装前端依赖。
2. 执行正式前端构建。
3. 通过 `prepare:github-pages` 写入显式 HTTPS 后端 Origin、`404.html` 和 `.nojekyll`。
4. 上传并部署 `client/dist`。

在 GitHub 仓库 Settings → Pages 中，把 Build and deployment Source 设为 GitHub Actions。工作流中的仓库身份、后端 Origin 和 `build.basePath` 必须与目标公开仓库一致；这些是公开部署转换，不应改动产品业务。

在仓库 Settings → Secrets and variables → Actions → Variables 中创建 `BACKEND_ORIGIN`，值为后端公开 HTTPS Origin，例如 `https://api.example.com`。Pages 工作流会拒绝缺失、非 HTTPS 或带路径的部署输入，再把该值写入静态产物的运行配置。

手工准备现有 dist：

```bash
npm --prefix client run prepare:github-pages -- --backend-origin https://api.example.com
```

参数必须是无路径 HTTPS Origin。脚本不会修改源码配置。

## 4. 部署后端

后端要求 Node.js 20 或更高版本：

```bash
npm --prefix server ci
npm run start:backend
```

运行配置来自 `config/backend.config.js`：

- `server.host`：容器或服务器通常使用 `0.0.0.0`。
- `server.port`：Node 内部监听端口，平台或反向代理转发到这里。
- `server.allowedOrigins`：精确前端 Origin 数组。
- `server.trustedProxyHops`：只信任与 Node 直接相邻的代理层数。
- `logging`：终端、汇总和可选 JSONL 文件轮转。
- `limits`：只能收紧代码硬上限，不能扩大代理能力。

后端注册两个公开入口：`GET /health` 只返回 `{"status":"available"}`，用于确认当前 HTTP 应用已经就绪；`POST /api/proxy/v2/request` 承担代理业务。健康入口不访问 Provider、上游或代理执行器，也不返回版本、主机和诊断信息。项目没有公开目录浏览、媒体代理或其它业务入口。不要把任意 URL 代理、CORS `*`、TLS 绕过或私网白名单加到部署配置。

## 5. Render 类 Node 平台

创建 Web Service，连接公开仓库并使用：

```text
Build Command: npm --prefix server ci
Start Command: npm run start:backend
```

平台公开端口必须转发到 `BackendConfig.server.port`。将 Pages 或其它前端的精确 HTTPS Origin 写入 `allowedOrigins`。Render 前置代理为一层时使用项目当前 `trustedProxyHops` 配置；代理层级不同必须按真实拓扑调整，不能盲目信任全部转发头。

Render 的 Health Check Path 设置为 `/health`。该检查只确认后端进程和 HTTP 路由可用，不代表任意 Provider 或上游站点可达。

Render 日志主要来自 stdout/stderr。`logging.console.format='compact'` 适合阅读，`json` 适合平台检索。免费或临时文件系统上的 JSONL 会随实例重建丢失，不能描述为持久日志；需要长期文件日志时挂载持久磁盘并把 `logging.file.directory` 指向该路径。

仓库还包含独立部署辅助工作流 `.github/workflows/render-keepalive.yml`。需要启用时，在 GitHub Actions Repository Variables 中配置：

- `BACKEND_ORIGIN`：与 Pages 使用的后端 HTTPS Origin 相同。
- `KEEP_BACKEND_WARM`：设为字符串 `true` 才允许定时任务执行；删除或改为其它值即可停用。

该工作流每 10 分钟请求一次 `/health`，也支持手动运行。它只服务免费 Demo 的部署保活，不属于播放器产品功能；GitHub 定时任务可能延迟，不能作为正式服务的可用性保证。

## 6. 反向代理

Nginx、Caddy 或平台网关负责公网 TLS、域名和转发，Node 仍监听内部地址：

```text
https://api.example.com
    -> reverse proxy
    -> http://127.0.0.1:3000
```

反向代理应：

- 只转发必要路径和方法。
- 保留请求体与响应状态，不解析 Provider 业务。
- 正确设置客户端转发 IP，并与 `trustedProxyHops` 一致。
- 配置请求体和超时不小于项目有效限制，也不无限放大。
- 不缓存代理 POST 响应，不注入 Cookie 或认证信息。

## 7. 前后端分离检查

1. 前端 `runtime.backendOrigin` 指向实际 HTTPS 后端 Origin。
2. 后端 `allowedOrigins` 包含浏览器地址栏中前端的精确 Origin。
3. 后端公网入口可返回 `GET /health`，并可接受 OPTIONS 预检和唯一代理 POST 路由。
4. Provider `networkHosts` 包含其信息请求的最小 host。
5. 媒体域名允许浏览器直连；项目后端不会代替媒体跨域或请求头。
6. 代理和应用日志没有 Cookie、Token、原始正文或用户数据。

## 8. 发布前验证

在部署输入提交上执行：

```bash
npm run build
```

部署后再检查首页、搜索、详情、播放、刷新深层路由、数据源切换、CORS 失败路径和设置页配置。发现产品缺陷时应先在开发分支完成修复和验证，再进入正式发布。
