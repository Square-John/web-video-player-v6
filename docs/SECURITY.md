# Security Policy

## 支持范围

安全修复面向当前 `main` 发布状态和正在准备发布的 `dev` 状态。已经退出当前协议的历史向量只供审计，不接受为了重新启用旧 ABI 或旧代理协议而降低安全边界的修复。

## 私下报告漏洞

请优先使用 GitHub 仓库 Security 页面中的“Report a vulnerability”创建私密安全公告。若仓库暂未启用该入口，请创建一个不包含漏洞细节的普通 Issue，请求维护者建立私密联系渠道。

不要在公开 Issue、讨论、日志或截图中提交：

- 可利用步骤、未修复 PoC 或真实攻击目标。
- Cookie、Token、Authorization、账号、验证码会话或私钥。
- 完整 URL 查询、请求/响应正文、媒体地址或 Provider 私有存储。
- 用户收藏、播放历史、IP 明细或其它个人数据。

报告应包含受影响提交或版本、环境、风险类别、最小复现条件、预期影响和建议缓解方式。可以使用虚构 host 与脱敏样本。

## 项目安全边界

- 单文件 Provider 获得用户信任后当前与应用同页执行；静态 AST 预检不是完整沙盒。只导入你信任且可审查的脚本。
- Provider 只能通过 SourceContext 使用受控网络、私有存储、挑战、日志和中止能力。
- 后端代理只接受受限 HTTPS 信息请求，逐跳执行 SSRF、DNS/IP、容量、并发和重定向检查。
- 媒体地址由浏览器直连，不受后端代理保护；用户应自行判断外部媒体服务是否合法可信。
- 项目不提供、不存储、不上传或分发媒体内容，也不保证外部站点持续可用。
- 日志禁止记录凭据、原始正文、完整路径查询、用户数据和 Provider 私有状态。

## 处理流程

维护者会先确认报告、评估影响和受影响版本，再在私密分支完成根因修复、兼容检查和回归验证。补丁准备完成后协调披露时间，并在不暴露利用细节的前提下发布升级说明。

安全修复不得通过关闭 SSRF/TLS 检查、扩大 CORS、信任任意转发头、隐藏错误、清理用户数据或绕过工程验证获得通过。

## 部署者责任

- 公网前后端使用 HTTPS，并精确配置 CORS Origin。
- 按真实反向代理层级配置可信代理，不信任任意 X-Forwarded-For。
- 保护服务器、日志目录和部署凭据，及时更新 Node.js 与依赖。
- 不公开 JSONL 日志下载接口，不把临时文件系统描述为持久审计存储。
- 只启用已审查 Provider，并遵守外部站点条款和内容权利。
